# MD Dog 1.1 App Store Release Design

## Goal

Prepare, archive, validate, and upload MD Dog 1.1 to App Store Connect without submitting it for App Review.

## Release scope

- Upload the iPhone and iPad app only.
- Use marketing version `1.1`.
- Start with build number `1`; increment it only if App Store Connect reports that build `1` already exists for version 1.1.
- Include the current uncommitted changes in `ContentView.swift` and `DonationStore.swift`.
- Do not create or upload separate macOS or visionOS builds.

## Preflight checks

Before archiving:

- Confirm the Release configuration compiles for a generic iOS device.
- Confirm the bundle identifier is `Mike-Yang.md-dog` and automatic signing uses team `T7Y3W9A2RX`.
- Confirm the 1024 × 1024 iOS app icon variants are valid.
- Confirm the generated Info.plist declares that the app does not use non-exempt encryption.
- Check localization, StoreKit product identifiers, and obvious release-blocking warnings.
- Preserve unrelated files and existing working-tree changes.

## Archive and upload flow

1. Build a signed Release archive for `generic/platform=iOS` using the shared `md dog` scheme.
2. Validate the archive for App Store distribution.
3. Upload the validated archive through Xcode's App Store Connect distribution flow, using the Apple account already signed in to Xcode.
4. Confirm that App Store Connect accepts the upload or begins processing it.

## Error handling

- If signing fails, inspect the exact certificate, team, entitlement, or provisioning error and repair only the required setting.
- Ignore malformed stale provisioning profiles only when Xcode can still create and validate the intended App Store archive; otherwise repair the profile issue before upload.
- If build 1 is rejected as a duplicate, change only `CURRENT_PROJECT_VERSION` to `2`, rebuild, revalidate, and upload again.
- If Apple validation reports metadata or binary issues, stop before upload when possible, correct the issue, and repeat validation.

## Completion criteria

The release task is complete when:

- The uploaded build is visible in App Store Connect as processing or processed.
- No App Review submission has been made.
- No release date, phased release, pricing, or storefront setting has been changed.
- The final report records the uploaded version and build number and any remaining App Store Connect work.

## Verification

- Record a successful Release build result.
- Record successful archive creation.
- Record successful App Store validation.
- Verify the uploaded build in App Store Connect or in Xcode's upload result.
- Re-check the repository status so the user can see exactly what was changed or committed.
